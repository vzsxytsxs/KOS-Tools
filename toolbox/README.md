# KOS Toolbox

Desktop application (WPF, .NET 8) that gathers KOS's tweaks, features and tools in one place. It reads the real system state, applies changes with verification, saves the previous state and knows how to restore it. On startup, only the overclock profile chosen on the GPU page and the color settings saved on the GPU Settings tab take effect again; nothing else is applied automatically.

> **Status of this version (0.2.0):** the core and the interface build without warnings (Debug and Release) and 187 core tests pass. The Devices, Processes and GPU pages and the power editor, as well as the additional tweaks, were opened on Windows 11 (reading of devices, interrupts and ghost devices, and the state of the tweaks, was checked; the rules process was tested on a test process). No interrupt write, device removal or new tweak has been applied on a real machine. Before using it, test in the KOS VM following the [VM test checklist](#vm-test-checklist).

The interface is entirely in English, with no language selector. The texts live in `src/KosToolbox.Core/Text/Txt*.cs` (the XAML uses `{x:Static t:Txt.Name}`); code comments are still in Portuguese.

## Build and publish

Requires the [.NET 8 SDK](https://dotnet.microsoft.com/download/dotnet/8.0) (or Visual Studio 2022 with ".NET desktop development").

```powershell
cd toolbox
dotnet test tests\KosToolbox.Core.Tests          # core tests
dotnet build -c Release                          # build
dotnet publish src\KosToolbox -p:PublishProfile=win-x64
```

Publish produces `toolbox\publish\win-x64\`: `KosToolbox.exe` (self-contained, does not need .NET installed) and the native WPF DLLs that must stay next to it. The WPF apps (the toolbox, KOS Firewall and KOS Equalizer) are published uncompressed and ReadyToRun, so each exe is about 240 MB. Measured on the development PC, the toolbox reached its visible window in 0.99 s instead of 1.48 s and held 140 MB of private memory instead of 194 MB (compressed, every assembly was unpacked into private memory at each start); most of what's left is WPF's own first-use warm-up. The toolbox is single-instance: a second start brings the first window forward.

**Where to install:** copy the whole folder to `C:\Program Files\KOS Toolbox\`. The toolbox reopens itself as administrator to change the system; in a folder that standard users can modify (Downloads, Documents, `ProgramData`), a file placed next to the .exe could run with those privileges. Outside `Program Files` it works, but shows a warning on Home.

## How it works

- **Real state.** Each tweak declares the settings that make it up and the value of each one per option. The state is computed by reading the system:
  - a highlighted button = all values match that option (only in that case);
  - **Partial** = some of the values match an option and the rest are missing or different; choosing an option applies the complete set;
  - **Not configured** = no value is stored and the absence is not one of the options (Windows uses its internal behavior);
  - **Unknown** = there are stored values, but none matches an option;
  - **Read error** = the read failed (e.g. BCD without administrator); it never appears as Disabled and blocks changes;
  - **Unavailable** = component missing from this installation, incompatible CPU, or a tweak with no effect in the current state (Start menu search while Open-Shell is the Start menu); the card is grayed out, with the reason below the description;
  - **Restart required** = written by the toolbox and only takes effect after a restart.
  - Lists show the state in italics when no option matches. `⋯ › Details and source` rereads the system and shows each value read, what is missing, which option each value satisfies and how the state was decided.
- **Applying.** Saves the current state, applies and rereads the system to confirm. A script's exit code is not proof of success; only the reread is.
- **No questions.** The button applies directly (remove, restore, delete and restart too); the result appears in a success, warning or error notification (toast). Options that reduce a protection or delete something irreversibly (firewall rules, critical startup items, unsupported MSI) apply and warn about the risk in a notification. Switching network adapter, monitor, DRS profile or power plan with pending edits discards them and warns. Files that a standard user may have swapped do not open as administrator (a warning instead of "open anyway"), and unsigned installers only open when the catalog knows the developer publishes them that way. Only two protections still use a dialog: the "Keep these display settings?" countdown (with no answer, the previous resolution comes back) and closing the window with a change in progress.
- **Administrator.** The toolbox opens as a standard user. When it needs administrator, it starts an elevated copy of itself (UAC) with a validated request: for tweaks, only the tweak and the option (the values come from the catalog); for startup, task, service, power and snapshots, the elevated process revalidates everything before writing. Cancelling UAC changes nothing.
- **Scripts.** Only scripts listed in the catalog, inside `%ProgramData%\TheKOS`, with a pinned SHA-256 and owned by SYSTEM/Administrators/TrustedInstaller when run elevated.
- **Logs** in `C:\ProgramData\TheKOS\Logs\Toolbox` (resolved through `CommonApplicationData`, without assuming the drive): `toolbox-YYYYMMDD.log`, a new part every 5 MB, 30-day retention and at most 60 files. The elevated process creates the folder and gives users permission to modify **only** `Logs\Toolbox` (not the TheKOS folder). If it cannot write, the toolbox shows a warning in English on Home and in Settings, keeps working and does not write elsewhere; the *Fix permissions* button prepares the folder with one UAC prompt. *Open logs folder* is in Settings.
- **Per-user data** in `%LocalAppData%\KOS\Toolbox`: `backups.json`, `startup-backups.json` (previous startup type of services/drivers), `pending-reboot.json`, `settings.json`, `interrupt-backups.json` (interrupt values before the first change to each device) and `process-rules.json` (old rules from the Processes page, read once by KOS Governor). Service snapshots live in KOS's own folder (below).
- **Animations** of 120–220 ms with easing on pages, tabs, groups (the arrow rotates), Network page sections, hover/pressed, selection, detail panels, dialogs, notifications, drop-down lists, menus and tooltips, the sidebar and smooth scrolling with the mouse wheel (the step follows the Windows lines setting; lists that scroll per item keep the default scrolling). Each new animation replaces the previous one (quick clicks do not pile up). Only the *Enable animations* option turns them on and off: the Windows animation setting (which KOS turns off) does not interfere, and WPF's own popup animations are off. Progress bars only appear with real progress (sources read, services read).

## Pages

The sidebar has the pages in groups: **Overview** (Home, KOS state), **Tune** (Windows, Power, GPU, Network, Peripherals, Audio), **System** (Startup, Services, Devices, BIOS), **Software** (Install, Windows Update, Debloat, Tools, Cleanup), **Diagnose** (Latency, Stability), then **KOS Apps** (KOS Governor, KOS Firewall and KOS Equalizer) and Settings. The KOS Apps entries are buttons with an open glyph, not pages: a click opens the app in front, or brings the running one forward (no second copy and no UAC prompt), and the page you were on stays selected. *Collapse* at the bottom shrinks it to the icons (the name in a tooltip) and the toolbox remembers it (`NavCollapsed`).

- **Home** (the toolbox always opens on it): live dashboard like Task Manager, read every second only while Home is open. A list on the left, **Hardware** (CPU, memory, GPU, each disk and network adapter: a live graph and a few values) and **System** (the rows below, each only when it has something to say), and the selected row's details on the right (graph, values and the tabs below); CPU is selected when Home opens:
  - *CPU*: live readings (usage, speed, parked, processes/threads/handles, uptime), processor (name, vendor, family/model/stepping via CPUID, microcode, socket, cores, threads, hyper-threading, base and bus clock, NUMA, virtualization in firmware), L1/L2/L3 caches from the Windows topology, supported instructions (SSE…AVX-512, AES, SHA, VT-x/AMD-V), motherboard and BIOS via SMBIOS, and the *Cores* tab with each logical processor (graph, usage, GHz, parked and the physical core; P/E on hybrid CPUs). Usage from kernel times; GHz and parking from the "Processor Information" counters.
  - *Memory*: live (in use, available, commit, cache, paged/non-paged pool), installed (total, used slots, type, speed, maximum capacity, ECC) and the *Modules* tab with each stick via SMBIOS (slot, size, type, rated and configured speed, ranks, manufacturer, part number, serial, width, voltages). The *SPD* and *Timings* tabs need access to the SMBus and the memory controller, which Windows only gives to a kernel driver; the toolbox does not install a driver: the *Read* button runs CPU-Z from the KOS tools folder (`tools\cpuz_x64.exe` or a subfolder, e.g. `tools\CPUZ_3.01`) in report mode (`-txt`, no window, ~10 s, with CPU-Z's own signed driver; elevated, only if the file belongs to SYSTEM/Administrators), reads the "Chipset" and "Memory SPD" sections and deletes the report. *SPD*: each stick (format, manufacturer, part number, ranks, voltage, JEDEC/XMP/EXPO tables and the register dump). *Timings*: memory and uncore clock, channels, rate in MT/s and CAS latency in ns, and the timings in the ASRock Timing Configurator layout (Primary, Secondary, Tertiary; value in a box). Filled box = read live from the controller by CPU-Z (tCL, tRCD, tRP, tRAS, tRFC, CR, tCCD…); hollow box = calculated from the SPD (DDR4, JEDEC 21-C Annex L, JEDEC rounding; tWR/tWTR/tRTP/tCKE/tREFI/tCWL from JESD79-4 when the SPD does not provide them) for the configured speed, which is what the BIOS uses on Auto; a value changed by hand in the BIOS does not appear in those boxes. ASRock reads everything directly from the controller's extended PCI space, which needs a kernel driver for that: CPU-Z only dumps the first 256 bytes, PawnIO's signed module (IntelMCHBAR) covers only Core CPUs (MCHBAR), and the drivers that read everything (AsrDrv, WinRing0) are on Microsoft's vulnerable driver list. With *Read memory SPD and timings at startup* (Settings, on by default; only with the toolbox as administrator), the read runs in the background when the toolbox opens.
  - *GPU* NVIDIA: all the sensors of the GPU page (NVML/NVAPI) live and the card (driver, PCI bus, VRAM, maximum PCIe link, power limit). Each physical disk (model, NVMe SSD/SSD/HDD via IOCTL, partitions with label and size, active time, response time, read/write from the "PhysicalDisk" counters); selecting a disk shows its graph and its health, read without a driver and without administrator: NVMe through the health log page (`IOCTL_STORAGE_QUERY_PROPERTY`: critical warnings, spare, life used, temperature, data read/written, power-on hours, power cycles, unsafe shutdowns, media errors) and SATA through `IOCTL_STORAGE_PREDICT_FAILURE` (the drive's own failure prediction and its SMART attribute table, with the life, temperature, reallocated/pending sectors and hours picked out). USB enclosures that don't pass SMART through just say so. Each physical network adapter (status, link speed, send/receive). Performance counters turned off in Windows just leave those fields empty. Under System, **System status**: power plan, the refresh rate of each display (and whether a higher one exists at its resolution), Resizable BAR and the GPU's PCIe link (NVIDIA: BAR1 window against VRAM, the card's and the link's top generation), BypassIO for DirectStorage on each fixed drive (`FSCTL_MANAGE_BYPASS_IO`: supported, or the driver that blocks it and why), crashes in the last 30 days (see Stability) and the current state of catalog tweaks (Game Bar, fullscreen mode, HAGS, NVIDIA P-states and MSI, MPO, VBS, memory integrity, hypervisor, Power Throttling, timer, useplatformtick, idle states, mitigations, Windows Update, UAC, firewall; unavailable ones do not appear). *KOS state* row when Windows isn't at the build and update number (`26200.7171`) of the last check on the KOS state page: Home runs the same read-only check once per build and, when items were put back, says how many (and the build before, when known) with *Review*, which opens the page; the row goes away once the page has checked this build. *KOS post-setup* row only when the last KOS RunOnce finished with warnings or errors: each one with what it means (from the KOS code in `PostSetup-Logs.txt` and the installer's exit code) and *Open logs*. *Pending changes*: the restarts the toolbox and Windows wait for; a row for the log warning appears when the logs have one. The KOS version, the post-install result and the warning about a folder outside Program Files are in Settings › About.
- **Windows**: categories Performance, Gaming, Visuals, System, Peripherals, Security and Connectivity, each with its sections (tables below). SmartScreen and Defender were removed from the interface, search, presets and catalog.
- **Startup** (Autoruns style): *Standard* mode (logon entries and tasks outside the Microsoft folder) and *Advanced* mode (also Microsoft and hidden tasks, every scheduled task whatever its trigger, Winlogon, Active Setup, services and the system hooks). Drivers only through the *Drivers* filter, with a warning; the system hooks also have their own filter. Columns Name, Source, Status, Startup type, Signer and Command; the running state of services is kept apart from the startup type (stopped is not disabled). Virtualized, grouped list, background reading with progress per source, icons loaded only when the row appears. One entry at a time; disabling never deletes anything:

  | Source | How it enables/disables | Restore |
  |---|---|---|
  | Run HKCU, HKLM 64 and 32 bit | `StartupApproved\Run` / `Run32` flag (the same one Task Manager uses) | the flag goes back to enabled |
  | Startup folders (user and all users) | `StartupApproved\StartupFolder` flag | same |
  | RunOnce (HKCU, HKLM 64/32) and Policies\Explorer\Run | read-only (no flag; Windows removes RunOnce after running it) | — |
  | Scheduled tasks with a startup or logon trigger (Advanced: every task, with each trigger named) | the task's `Enabled` (Task Scheduler COM) | re-enable the task |
  | Winlogon `Shell`, `Userinit`, `Taskman`, `AppSetup` (HKLM and the per-user Shell), Advanced | read-only: a wrong value can stop sign-in | — |
  | Active Setup (`Installed Components\*\StubPath`, 64 and 32 bit), Advanced | read-only: the entries belong to their installers | — |
  | Services (Advanced) and drivers (own filter) | startup type through the SCM (`ChangeServiceConfig`); the previous one is saved | goes back to the saved type; with no record, Manual |
  | System hooks, Advanced (own filter): AppInit DLLs (64 and 32 bit, with whether `LoadAppInit_DLLs` is on), image hijacks (IFEO `Debugger`, 64 and 32 bit), boot execute (`BootExecute`), LSA authentication, notification and security packages, print monitors, known DLLs, Winsock transport and name-space providers | read-only: they belong to Windows or to the program that added them, and a wrong change can stop Windows from starting or signing in | — |
  | WMI subscriptions (`root\subscription` consumers that run a command or a script: `CommandLineEventConsumer`, `ActiveScriptEventConsumer`), Advanced, with the system hooks | read-only (read through `Get-CimInstance`) | — |

  Disabling critical items (Boot/System or severe ErrorControl) and Windows components applies and shows the reason for the risk in a notification. The image hijacks KOS itself sets (Game Bar and Search programs pointed at `systray.exe`, which exits) are labelled as set by KOS, with the note that the toolbox setting that turns the feature back on removes them. Only Explorer add-ons and codecs aren't covered (the line under the list names what was read and what wasn't).

  **Signer** (read after the list shows, several files in parallel): the file's own Authenticode signature, else the Windows catalog that lists its hash (how most Windows files are signed), else *Not signed* or *File not found*. Host programs that run another file (wscript, cscript, cmd, PowerShell, rundll32, mshta, regsvr32, msiexec…) show their signer followed by the host's name, since it says nothing about what they run. For display only: nothing is run or refused because of it. *Hide Microsoft-signed* hides entries whose file Microsoft signed (not the compatibility signature Microsoft gives other companies' drivers); entries run by a Windows host, unsigned and missing files always show.

  **Delayed start** (details panel of a Run entry; not RunOnce or policy entries): *Starts* At sign-in / 30 s / 1 min / 2 min. A later start turns the Run entry off through its `StartupApproved` flag (the value stays, so it can be turned back on) and creates the scheduled task `KOS delayed start - <name> [HKCU|HKLM <key>]` (`schtasks` with an XML definition, written to an admin-only folder when elevated): a logon trigger with that delay, least privilege, no time limit, runs on battery, the same command. A user's entry gets a task of that account; an all-users (HKLM) entry gets one for every member of Users, as the Run entry was, and needs the toolbox as administrator. The task is read back in full (command, arguments, delay, account or group, run level) before the entry is turned off; if that or turning the entry off fails, the task is deleted again. *At sign-in* deletes the task and turns the entry back on; *Enable* and *Remove* also delete the task, so the program never starts twice.
- **Power**: KOS profiles and hibernation (catalog) and a plan editor: choose the plan by name (the active one appears as "Name — Active"), activate, AC/DC, search, subgroups and settings enumerated through PowrProf, names and descriptions in English, units, a list for enumerated values and a validated numeric field (minimum, maximum and step) for ranges. Settings without metadata are read-only. *Show advanced settings* shows the hidden ones. The edited plan is separate from the active one; changes stay pending with *Apply*/*Discard*, switching plans with pending changes discards them (with a notification), and after writing the plan is reread and each value is checked. Managing plans: *Save a copy* (PowerDuplicateScheme), *Rename* (name and description; only what changed is rewritten, so the translated text of Windows plans is not lost), *Delete* (refuses the active plan), *Import…*/*Export…* (.pow; export through `powercfg /export`) and *Restore default plans* (the button's tooltip says what Windows deletes, including KOS plans). Each setting's ⋯ menu has *Custom value…* (decimal or 0x hex, outside the list), *Discard change*, *Remove value (use plan default)* (deletes ACSettingIndex/DCSettingIndex from the plan; the *Default* badge marks settings without their own value) and *Show/Hide in Windows power options* (ATTRIBUTE_HIDE of the setting itself, applies to all plans; refused when the whole subgroup is hidden); the *Hidden* badge marks the hidden ones. *Compare with other plans* shows the value saved in each other plan and marks *Differs*; *Only settings that differ* filters. Operations that need administrator go through the elevated process (`PowerPlan`, validated there) and each one is checked by rereading Windows.
- **Windows Update** (System, after KOS state; administrator): lists the updates Windows Update offers this PC (`IUpdateSearcher.Search("IsInstalled=0 and IsHidden=0 or IsInstalled=0 and IsHidden=1")` through the Windows Update Agent COM API: title, KB, category, size, hidden) and installs the checked ones one by one (download, then install, so one failing doesn't stop the others; the EULA is accepted as Settings does when you choose Install), or hides them (`IsHidden`; a mandatory update can't be hidden) and shows them again. Nothing runs on its own and the search only runs on the button. Windows Update stays in the mode set on *Windows › System › Windows Update*: each operation records and then removes the two policies that block it (`DisableWindowsUpdateAccess`, `DoNotConnectToWindowsUpdateInternetLocations`), puts wuauserv, BITS and Delivery Optimization on manual only if they were disabled (in the registry and through the Service Control Manager, which otherwise keeps them disabled until a restart and the search waits forever; Delivery Optimization refuses administrators, so it goes through PowerRun, and downloads fail without it), checks that wuauserv starts (an error instead of a hang if Windows still has it disabled), runs, then stops the services it allowed and writes every value back, reading each one again (a value that doesn't read back is an error naming it). If the toolbox dies in the middle, the next startup's `windows-update-policy.cmd` disables the services again. After an install it points to *KOS state*, since updates can put back what the KOS changed. Replaces `tools\wumt_x64.exe`, removed from KOS-W11.
- **KOS state**: what Windows Update, `sfc` or `DISM` put back after the KOS changed it. The check runs on every visit (read-only, a few seconds, with a progress bar) and compares: the catalog settings that have a KOS default (for the current security profile) with that default; the registry values, deleted keys and scheduled tasks of `KosState/kos-expected.json` (a copy of KOS-W11's `bin\2\kos-expected.json`, embedded; values a catalog setting owns are checked as that setting, and services or autologgers this installation doesn't have are skipped); and every other value of the KOS keys (`snapshotKeys`) with the last good state (a `WOW6432Node` key Windows shares with the 64-bit one is compared once, as the 64-bit key). It also checks what the image build removes: apps (`packages`, and the NTLite `components` that are apps, by package name: every user's and the provisioned ones as administrator, the current user's otherwise; components that aren't apps can't be seen with Windows running), optional features and capabilities (`features`, through DISM: administrator only) and deleted files and folders (`files`). Three sections: *Changed outside the toolbox* (checked), *Other changes in the KOS keys* (checked) and *Changed in the toolbox* (unchecked: the history says the toolbox left it that way). *Apply checked* puts catalog settings back through the normal path (warnings at the end, like *KOS defaults*) and the rest through `KosStateFix`: HKCU in the toolbox's own process, HKLM/HKCR, deleted keys and tasks directly as administrator or in the elevated process (Windows Update's own tasks refuse administrators and go through PowerRun), which only receives ids (`e:N`, `k:N`, `t:N`, `s:N|name`, `p:N`, `c:N`, `f:N`, `x:N`; apps are removed for every user and deprovisioned, features only turned off or on, never removed, capabilities removed, files deleted as TrustedInstaller through PowerRun when no link is on their path (a `SystemApps` folder only after its app is removed); Defender's own files are in use while it runs and wait for the Safe Mode step) and takes the values again from the embedded list or the admin-only last good state (HKCU ids, values a catalog setting owns, data with %variables%, and snapshot values that don't differ right now are refused there; a snapshot value's name and data come from the registry and the reference, never from the request). Then it checks again and reports only what reading back confirmed. The last good state is saved after a check with nothing to fix and after applying, for each part only when every write in it worked (what was left unchecked is kept; a failed write never becomes the last good state): the machine part in `%ProgramData%\TheKOS\Baseline\kos-lastgood.json` (administrator only, `PrepareDirectory`; read only when SYSTEM or Administrators own the folder and file), the user part in `%LocalAppData%\KOS\Toolbox\kos-lastgood-user.json`. Until there is one, the setup's baseline (`Baseline\kos-baseline.json`, written by the KOS setup before its restart) is used, its HKCU part only for the account that ran the setup. Without administrator a few protected keys can't be read; the page says how many and offers *Restart as administrator*. The *Repair Windows* tab runs `sfc /scannow`, `DISM /Online /Cleanup-Image /RestoreHealth` and three component store (WinSxS) tools: *Component store size* (`/AnalyzeComponentStore`: real size, what backups and replaced versions take, the last cleanup and whether one is recommended; changes nothing), *Component store cleanup* (`/StartComponentCleanup`: removes the versions newer updates replaced, which every update installed since the KOS image was built leaves behind) and *Component store cleanup with ResetBase* (`/StartComponentCleanup /ResetBase`: also the old versions each installed update keeps, which frees the most; afterwards the installed updates can't be uninstalled, which a warning toast repeats when it finishes). They run one at a time (`KosState/WindowsRepair.cs`), as administrator directly or through the elevated process (which only receives the tool's name and a run id), each with its own progress bar read from the percent the tool prints; progress and the result go through `%ProgramData%\TheKOS\Toolbox\Repair` (`PrepareDirectory`). When DISM can't find its source files (`0x800f081f` and similar) it says to set Windows Update to on or paused and run it again. After sfc or the DISM repair, the tab suggests checking the KOS state.
- **Services**: service snapshots in C# (below).
- **Devices**:
  - *Interrupts*: connected PCI devices (SetupAPI) with the support reported by Windows (Line/MSI/MSI-X, `DEVPKEY_PciDevice_InterruptSupport`) and the values in `Enum\<id>\Device Parameters\Interrupt Management`: `MSISupported`, `MessageNumberLimit`, `DevicePolicy`, `DevicePriority` and `AssignmentSetOverride` (processors, with the *Specified processors* policy). *Only devices that support MSI* filter (on by default). Editing a device saves the original values on the first change (*Restore original*), writes (elevated and revalidated: only a connected PCI device and valid ranges) and rereads. Turning MSI on for a device with no reported support writes and warns about the risk in a notification. Takes effect after a restart.
  - *Ghost devices*: devices not connected right now, grouped by class, with the last connection date. Checking and *Remove checked* uninstalls the entry (`DiUninstallDevice`, as in Device Manager), without deleting drivers. *Check all* then *Remove checked* removes them all, except devices with an interrupt affinity set (`Affinity Policy`: `DevicePolicy` 3 or more, or a non-zero `AssignmentSetOverride`), which are marked and stay unchecked so they keep it if they come back. The elevated process refuses connected devices; the result is checked by rereading the list.
- **BIOS** (like SCEWIN GUI, through AMI SCEWIN from the KOS tools folder: `tools\SCEWIN\SCEWIN_64.exe` with `amifldrv64.sys` and `amigendrv64.sys` in the same folder):

- **Processes** left the toolbox: process rules are now **KOS Governor** ([`../governor`](../governor/README.md)), a separate program. On first launch it imports the rules from `process-rules.json`. `KosToolbox.exe --governor` (the old Run value) only removes that value and exits.
- **Storage**:
  - *Disk usage*: choose a disk or folder and sum the size of each folder (normal file system enumeration, without following junctions/links or counting cloud-only files; file size, not size on disk, so hard links such as those in WinSxS count more than once). Sorted list with % of parent, navigation by double click/*Up*, the 100 largest files and *Show in Explorer*. Nothing is deleted in this tab.
  - *Compression* (Disk usage tab): an algorithm (XPRESS4K, XPRESS8K by default, XPRESS16K, LZX) and *Compress*/*Uncompress* for the selected folder, or the one shown. It uses Windows' executable compression (`compact /C /A /I /EXE:<algorithm>`, the same WOF compression CompactOS uses; `compact /U /A /I /EXE` to undo), run folder by folder from a walk that skips links, never with `/S` (which follows junctions): files stay readable by every program and are decompressed in memory as they are read. Reports the size on disk before and after (`GetCompressedFileSize`) and the files processed so far; files in use are left as they are (the game must be closed). Refuses the Windows folder (Windows decides that itself with CompactOS), drive roots, a folder that is itself a link or sits under one, and a folder with a junction or symbolic link (folder or file) anywhere inside it; each folder's path is checked again just before compact runs on it, and the run stops if one became a link. After compressing, a warning when the folder holds a DirectStorage game (`dstorage.dll`): compressed files can't use BypassIO, so loading can get slower; and a reminder that a game update rewrites the files it changes uncompressed.
  - *Cleanup*: fixed categories (user and Windows temporary files older than 1 hour, thumbnail cache, INetCache, user and system error dumps and reports, shader caches, Windows Update downloads, all of `Windows\Logs`, the Delivery Optimization cache, the Windows Installer patch cache `$PatchCache$`, the previous Windows installation `Windows.old`, Prefetch, Recycle Bin). `Windows.old` belongs to TrustedInstaller, so Windows' own Disk Cleanup handler removes it (`VolumeCaches\Previous Installations` through `cleanmgr /sagerun` with a set number of the toolbox's, unmarked afterwards); a `Windows.old` that is a link or isn't owned by SYSTEM, Administrators or TrustedInstaller is refused. Every other delete opens the listed file or empty folder without following links, checks the handle's real path is still the listed one (no junction swapped into a parent since the listing) and deletes through that handle; a root that is a link isn't entered. *Analyze* measures; *Clean selected* measures each category, deletes only files (those in use are skipped; root folders stay; empty subfolders go) and measures again to report what was freed. System categories go to the elevated process only as ids; the paths come from the `JunkCleaner` catalog.
- **Apps**:
  - *Programs*: the same entries as Settings › Apps (Uninstall keys of HKLM 64/32 bit and HKCU, without system components or updates), with publisher, version, size and date. *Uninstall* runs the program's own uninstaller (MSI with `msiexec /x {code}`) and rereads the list to confirm; *Open install location*.
    - The wait also follows the processes the uninstaller started (NSIS ones copy themselves to `%TEMP%` and the original closes right away). It ends when they all close or when the entry disappears from the list for 3 s.
    - **Leftovers** (like Revo, Geek and HiBit): before uninstalling, the toolbox stores the program's name, publisher, folder and `.exe` files. When it leaves the list, it searches for what remained and shows a list to review, grouped and with the reason for each item. Everything comes checked, and nothing goes without *Delete checked*.
    - **What the search finds:**
      - the leftover install folder;
      - folders named after the program (or publisher\program) in AppData (Roaming, Local, LocalLow, Local\Programs), Program Files and ProgramData, including .NET settings ones (`app.exe_Url_…`);
      - Start menu and Desktop shortcuts to the folder, and Start menu folders with the name;
      - `Software\<program>` and `Software\<publisher>\<program>` (user, machine and WOW6432Node);
      - the leftover Uninstall entry and the Windows Installer record (by product code);
      - traces with the program's path: Run/RunOnce, App Paths, MuiCache, compatibility (Layers and Compatibility Assistant), FeatureUsage (`{GUID}\…` paths are translated), tray icons (NotifyIconSettings), `Tracing\<exe>_RASAPI32`;
      - services and scheduled tasks that run from inside the folder.
    - **Safeguards:**
      - generic names (Microsoft, Windows, Update, Steam, bin…) do not match, and a name that another installed program also has does not count (Python 3.11 and 3.12);
      - nothing that is, contains or is inside another installed program's folder; if the folder is shared (the Riot Client of LoL and TFT), traces by path do not count;
      - never Windows, the roots (Program Files, AppData, the profile, Documents…), `AppData\Microsoft`, `ProgramData\Microsoft`, Package Cache, WindowsApps, the KOS folder and the toolbox's;
      - in the registry, only below a fixed list of keys, outside `Software\Microsoft`, `Software\Classes` and `Software\Policies` (with exact exceptions: Uninstall, App Paths, Tracing, PolicyCache…);
      - the publisher's folder and key (or a folder above the program's, such as `Local\Thorium`, which holds the browser profile) only go if they end up empty, and so do Start menu folders that only match by name;
      - the program's folder only serves to find traces by path if it is not protected (an entry pointing to System32 finds nothing);
      - an HKCU Uninstall entry (which the account itself can write) and Store apps only lead to the account's items (HKCU and the profile), never the machine's;
      - short 8.3 names (`PROGRA~1`) are expanded before comparisons, and one that cannot be expanded is refused;
      - links (junctions, symbolic) are never followed: the link goes, the target stays.
    - **When deleting:** files and folders go for good (no Recycle Bin, by the maintainer's choice). Keys and values are first saved to `.reg`, services to `.reg` and tasks to `.xml` in `%LocalAppData%\KOS\Toolbox\leftovers-removed\`. The search runs again and the list shows only what remained. Machine items (HKLM, Program Files, ProgramData, services, tasks) only go with the toolbox as administrator.
    - **Force removal:** for a broken or missing uninstaller. The same search, including the program's folder and entry, without running the uninstaller.
    - **Uninstall checked (N):** the list has a box per program; the checked ones are removed one after another, silently when the uninstaller allows it (MSI with `msiexec /x {code} /qn /norestart`, the entry's own `QuietUninstallString`, an Inno Setup `unins000.exe` with `/VERYSILENT /SUPPRESSMSGBOXES /NORESTART`, an NSIS uninstaller, recognized by the marker in its file, with `/S`), otherwise with its own wizard. Only machine-wide entries (HKLM) whose uninstaller is in Program Files, Windows or the installers' package cache run silently: a user's own entries (HKCU) could name any command or product, so they always open their wizard. Each one is confirmed by re-reading the list; one that fails or is still listed is named at the end and the rest go on. Then one leftovers search for all the removed programs, in one list to review (an item that several of them share appears once).
  - *Store apps*: current user's packages through `Windows.Management.Deployment.PackageManager` (Apps / System apps / Frameworks / All filter). *Remove* removes only for the current account and checks by rereading (system apps and frameworks may take with them features that depend on them). With *Every user and new accounts* (toolbox as administrator), it removes the package for all users (`RemoveForAllUsers`) and deprovisions it (`DeprovisionPackageForAllUsersAsync`), so new accounts and feature updates don't bring it back; a system app is first marked end-of-life for each user that has it and deprovisioned in `AppxAllUserStore`, the way servicing retires apps, which lets Windows remove it. Then it looks for the package's leftovers in the account: the `AppData\Local\Packages\<family>` folder, the BackgroundAccessApplications, PolicyCache and notification keys with the package name, and the MuiCache with its path. The AppX database (StateRepository) is not touched. Needs the AppXSvc service: with "Microsoft Store services" disabled, the tab warns instead of listing. *Search in Microsoft Store* opens the Store search.
  - *Windows features*: the "Turn Windows features on or off" list through the official `dism.exe` with `/English` (same output in any Windows language); when selected, it shows name, description and whether a restart is needed (`/get-featureinfo`). *Turn on* (`/enable-feature /all`, also turns on dependencies) and *Turn off* run DISM and check by rereading the list. DISM requires administrator even to list.
- **Network**: choose the adapter (physical ones; *Show virtual adapters* includes the virtual ones), shows status and speed and lists the advanced properties the driver describes in `Control\Class\{4d36e972-…}\NNNN\Ndi\Params` (those of the Advanced tab in Device Manager): a list for `enum`, a field validated by minimum/maximum/step/base for numbers and by length for text. *Default* badge when no value is stored; *Use driver default* deletes the value. Pending changes with *Apply*/*Discard*; *Apply* writes REG_SZ like Device Manager (elevated and revalidated against the driver's `Ndi\Params`), restarts the adapter through SetupAPI (DIF_PROPERTYCHANGE, like `devcon restart`) and rereads. *Restore original* goes back to the values saved before the first change of each property (`network-backups.json`). Settings KOS knows that the driver does not describe stay hidden; the ⚠ *Show settings this driver doesn't list* button shows them and, when on, makes *Recommended* apply those too (written to the Registry; the driver only uses them if it supports them). Global TCP parameters (`netsh int tcp`) were not integrated: netsh's output is translated according to the Windows language. **DNS** (own section per adapter; applies right away, not a pending change): *Automatic (DHCP)*, *Cloudflare*, *Google* or *Quad9*, each with its IPv4 and IPv6 servers, and *Encrypt (DNS over HTTPS)*, which uses the DoH templates Windows already knows for those servers, with no fallback to plain DNS (a warning toast says names won't resolve while the provider can't be reached over HTTPS; not offered with DHCP's servers). Written with `SetInterfaceDnsSettings`, as Settings › Network does (encryption is cleared before the servers are replaced; an adapter without IPv6 gets only the IPv4 servers); as a standard user through the elevated process, which receives only the adapter, the choice and the encryption flag. Read back to confirm; the section shows the servers Windows is using and names other servers set by hand.
- **Peripherals** (Tune group, after Network; no administrator): the HID devices connected now, over plain HID (`hid.dll` and SetupAPI, no vendor software, no kernel driver), to configure gaming mice and read device batteries. A device is talked to only when a driver claims it by exact VID + PID **and** the collection it needs; every other device is listed as *Not supported* and nothing is sent to it.
  - *Drivers* (`KosToolbox.Core/Peripherals/<Vendor>`, a pure codec plus a driver over `IHidTransport`; `PeripheralRegistry` tries vendor drivers in order, then battery-only readers on devices nobody claimed): **Razer** mice (90-byte feature report on the 91-byte collection, the mouse collection MI_00 on the Viper Ultimate; firmware, serial, battery and charging, DPI and stages, polling rate legacy or extended, picked by which getter answers, sleep timer, low-battery threshold, logo brightness, and the extended-matrix effect of the light (`0F/82`, `0F/02`: off, static, single-color breathing, spectrum; others read as *Other* and aren't written); brightness, effect and, on a generation that reads its DPI live, the DPI are written stored and live and both read back (the Viper Ultimate keeps them apart: a stored write alone left its light dark and its live DPI unchanged); catalog `RazerCatalog`: Viper Ultimate `007A`/`007B`, the Mouse Dock `007E` (ring light only), DeathAdder V2 Pro, and the upstream-verified Viper V2 Pro, Naga V2 Pro, DeathAdder V3 Pro, Viper V3 HyperSpeed). The transaction id comes from the catalog; when it gets no answer, the other ids are tried with getters only, and setters use only an id that answered. **Logitech HID++ 2.0** (receivers and wired G mice; name, firmware, battery 0x1004/0x1000/0x1001, DPI 0x2201, report rate 0x8060, onboard-profile mode 0x8100; live writes only in host mode or on a cable; *Use host mode* switches a receiver mouse, no profile sector is ever written; HID++ 1.0 devices give their battery from register 0x0D). **Feature-report 64-byte** (Glorious, Hitscan, G-Wolves) and **report-8** (Redragon, Pulsar, Hitscan) families: battery only. **Keyboards**: **ROYUAN gen2** magnetic boards (`RoyuanDriver`, 64-byte feature report 0 on collection `FFFF:0002`; catalog `RoyuanCatalog`: the Attack Shark R82HE, `3151:502D`, board id 2844). The PID is shared by dozens of boards, some of another command family whose same opcodes write other registers, so the first read sends Identify (`0x8F`) and nothing else until it names a catalog board; the codec builds only allow-listed opcodes (never flash erase, bootloader, sensor calibration or factory reset; the per-key picture upload only through the paced path below). It reads firmware (the travel unit follows it: 0.005 mm from 5.00), polling rate (8000..125 Hz), the stored lighting (static, breathing and spectrum with their color; other modes read as *Other*; no *Off*: mode 0 isn't confirmed, brightness 0 is), brightness in five steps (a percentage is rounded to 0/25/50/75/100), the active onboard profile (1..4) and the switch columns of the active profile (actuation, release point, rapid-trigger steps, bottom dead zone, key mode). Every write goes to the keyboard's flash: sent once, at least 300 ms after the previous one, then the driver polls Identify until the board answers again (while it stores it drops packets and echoes requests; a column sent 100 ms after a commit was lost on the R82HE), then reads it back. *Switches* sets the same travel on every key (read-modify-write of whole columns, `last` on each column's final page only, slots without a key and each key's mode bits 0..6 kept; the release point follows the actuation) and warns when the keys differ now. *Key travel* turns on the live stream (`0x1B`, a RAM flag): input reports on `FFFF:0001` with a 512-report queue, shown as the key's slot and millimetres and as the key filling up on the keyboard picture; it's turned off when the device or the page is left, before any write or read, and when the process exits. **Per key**: the keyboard is drawn from the catalog's layout (the R82HE's 80 keys; the matrix is column-major, slot = column × 6 + row; which key each slot is comes from the board's own keymap, `0x8A`, checked with the travel stream), each key with its label and actuation; clicking keys chooses them and the Switches editor then shows and sets those keys only. *Key mode* (one key; two for snap tap): normal, snap tap (both keys kind 7 and each other's slot, sub-op 9; a pair that's left is undone on both), toggle (kind 4, or 5 repeating), mod-tap (hold time in sub-op 5, hold and tap keys in sub-layers 0 and 1), dynamic keystroke (first point in sub-op 4, four action bytes through sub-op 8, read in bulk through sub-op 10, up to four keys in sub-layers 0..3); keymap entries go first (`0x0A`, one slot, stored at once), then the columns, the snap partners one slot at a time (`65 09 00 slot`: a whole partner column is rebuilt by the board on apply and read back 255 on the R82HE). *Remap* (one key): its base key and its Fn-layer key (`0x10`/`0x90`, Windows layer; an entry the list doesn't offer, like a consumer key or a lighting control, is shown and kept unless another is chosen) and *Restore default* from the catalog's copy of the board's factory keymap. *Macros*: the driver reads the 50 onboard slots (`0x8B`) and has the write (`0x0B` in 56-byte pages; text steps `key down|up ms`, `Mouse1..5`; bound to the chosen key as repeat-count, toggle or while-held), but the page shows the macro editor only for a catalog board marked as keeping macro writes, none yet: on the R82HE a saved slot read back unchanged, with one page and with all five, and the test steps were in no other slot. *Per-key colors* (`0x0C`, light mode 13): the keyboard can't report its picture (its read returns old data), so the page paints its own and sends it whole, at least 10 s between uploads, pages 100 ms apart, 2 s to settle (fast uploads stall the endpoint until USB is reconnected), and the toast says the colors were sent but not confirmed. Not offered: gamemode (every write is stored), the board options (`0x89`: its reply keeps the request's checksum at byte 7, so the vendor driver's field layout doesn't hold), firmware (`KOS-private` research only: the bootloader takes any image with a matching byte sum). VIA/QMK boards by their `FF60:0061` collection (protocol version and layer count, read-only; the shared ODM VIDs are refused, `3151:502D` is the ROYUAN driver's) and Wooting (recognised, nothing read yet) are *Untested model*. **Battery-only readers**: SteelSeries Aerox/Prime/Rival 3 Wireless and Arctis 7/Nova Pro Wireless, Corsair Void and Bragi, HyperX Cloud III Wireless (one read-only query each), DualShock 4/DualSense (their own input report; nothing sent). **DualShock 4 on its cable** (`PlayStationDriver`, checked on a v2, `054C:09CC`): the light bar is written through output report `05` (light-bar and blink flags only, so rumble is left alone; *Off* is black), a color or off. The controller can't report its light bar, so the page shows the last color sent from this toolbox and says so; it goes back to the default when the controller disconnects, and Steam or DS4Windows, while running, set it themselves. Its polling rate is counted from 0.5 s of input reports and shown, not offered: the controller asks USB for its interval (250 Hz on the v2), and changing it takes a USB filter driver. Its gamemode profile is the light bar (*Keep*, *Off* or a color); since the bar can't be read, saving the profile also saves the color the page last set as the one gamemode puts back (so it must be set on the page first), and setting another color on the page later updates it. *Lighting sync* includes it for *Off* and *Static* only. Bluetooth devices (the battery Windows keeps, by container id). `HeadsetControl` (an optional separate program in the KOS tools folder) has its runner and JSON parser in Core but isn't wired to the page yet.
  - *Rules*: getters retry, a setter is sent once and never again on a lost reply; every write is validated against the catalog, read back, and the toast reports what the read-back shows (an error toast with the value the device has on a mismatch); read-modify-write for the DPI stage table; an *Untested model* gets a warning toast after each write; no firmware, DFU, bootloader, reset, pairing or calibration command exists in the code. A running Synapse or G HUB shows a warning on the device. After a polling-rate change the toast points to Latency › Mouse.
  - *Gamemode profile* (administrator): per device, what KOS Governor sets while gamemode is on: *Set the DPI* (a switch and a slider), the polling rate (*Keep* or a rate), the *Light* (*Keep*, *Off* or an effect with its color; the dock's *Ring*: *Keep*, *Off*, *Battery*, *No battery*) and, on the R82HE, *Rapid trigger* (*Keep*, on with one step for press and release, or off; each key's actuation kept). Mice and the dock get live values only; the R82HE stores every setting, so gamemode writes its flash on each start and stop (a warning says so). *Save* checks the values against the device and writes `gamemode-peripheral.json` (see the governor README); *Remove* takes it out. For example 1000 Hz, mouse logo and dock ring off in gamemode, everything back when it ends.
  - *Lighting sync* (under the device list, with two or more devices whose light the toolbox writes; a dock showing the mouse battery is left out): check devices, pick *Off*, *Static*, *Breathing* or *Spectrum* and a color. *Apply to all* writes each device in turn, each read back (*Off* is brightness 0 on the R82HE, whose brightness goes to 100 % with an effect if it was 0). *Use in gamemode* puts the same light in each checked device's gamemode profile, the rest of each profile kept.
  - The R82HE is talked to by one KOS program at a time (a named mutex per VID/PID around every read and write): the toolbox and KOS Engine reading it together corrupted each other's replies, and a whole-column write made from such a read would land on every key.
  - *Mouse battery on the ring* (Mouse Dock, administrator): *Turn on* sets `DockBattery` in `gamemode-peripheral.json` and KOS Governor colors the ring live by the mouse battery; *Turn off* clears it and writes the effect stored in the dock back (stored and live, read back).
  - *Reading*: SetupAPI lists the HID interfaces (`HidD_GetHidGuid`); each path is one top-level collection, opened with access 0 (read/write sharing) only for `HidD_GetAttributes` (VID/PID, revision), `HidP_GetCaps` (usage page, usage and input/output/feature report lengths) and `HidD_GetProductString`. The USB interface comes from `&mi_xx` in the path and the collection number from `&colNN`. Collections are grouped into one physical device by the node's `DEVPKEY_Device_ContainerId` and VID/PID; without one (or with the container every built-in device shares), by VID/PID and the parent instance in the path, which keeps one interface's collections together. FIDO security keys (usage page `F1D0`) are recognised from their hardware ids and never opened. Bluetooth is shown when the node's parent is on the Bluetooth bus; a USB device shows no connection, since a USB receiver isn't "wired".
  - *Page*: the device list on the left, supported devices first (icon by kind, name, connection, VID:PID, battery with *charging* or *Asleep*); the selected device's controls in the middle; on the right its picture, which stays in place while the controls scroll (above the controls, smaller, when the window is near its minimum width). The picture of a mouse is a rendered mouse (`Assets/mouse.png`, the same for every mouse); the Mouse Dock, headset, keyboard and controller are drawn in XAML; the light glows on it in the color and brightness the controls show, before *Apply*. The DPI slider is logarithmic (400, 800 and 1600 sit apart). Controls: Performance (DPI as a slider in the device's steps plus a box and *Apply*, the stored stages as a segmented choice of the active one, the onboard profile as a segmented choice, polling rate as a segmented choice, four to a row), Lighting (brightness as a slider plus a box and *Apply*, the effect as a segmented choice that applies on click, the color from presets or as `#RRGGBB` with *Apply*: on off or spectrum it switches to static; on the dock, *Mouse battery on the ring*), Switches (magnetic keyboards: actuation slider and box in the board's step, rapid trigger with its press and release steps, bottom dead zone, one *Apply* and a warning toast that it is stored in the active profile; *Show key travel*), Gamemode profile (not on devices whose writes are all stored), Power (battery with *Show in the tray*, which turns that device's battery icon in KOS Governor's tray on or off, sleep timer, low-battery threshold). A slider only moves its box and the picture: *Apply* is the one write. Each control is shown only when the driver read it and editable only when it can write it, then Info (VID:PID, product string, protocol, connection, revision, firmware, serial) and its HID collections (interface, collection, usage page:usage, report lengths with the id). *Copy device report* puts that as text on the clipboard for a support request, without the device path or instance id (they can carry a serial number or a Bluetooth address). Read on every visit and on Refresh (supported devices one after another, getters only); batteries again every 60 s while the page is shown; the list again 2.5 s after the last `WM_DEVICECHANGE`/`DBT_DEVNODES_CHANGED` (hooked on the main window, which gets it without registering).
  - *HID layer for the device drivers* (`KosToolbox.Core/Peripherals/Hid`, AOT-safe for KOS Engine: `DllImport` with blittable types, no COM, WinRT, `dynamic` or reflection JSON): `HidHandle.OpenFeatureOnly` (access 0, for `HidD_GetFeature`/`HidD_SetFeature` even on collections Windows holds) and `OpenReadWrite` (overlapped, for output and input reports), overlapped `WriteFile`/`ReadFile` with a timeout (500 ms default; on timeout `CancelIoEx`, then `GetOverlappedResult` waits for the cancel), `HidD_GetInputReport`, `HidD_FlushQueue`, one request at a time per physical device, and `IHidTransport` for the drivers. Every report buffer starts with the report id and has exactly the length `HidP_GetCaps` gives, zero-padded; a payload that doesn't fit is refused. The drivers use only `IHidTransport`; xUnit drives them with a scripted transport (`PeripheralDriversTests`).
- **Audio** (Tune group, after Peripherals; no administrator): the active playback and recording devices through Core Audio (`KosToolbox.Core/Audio/AudioDevices.cs`, COM, off the UI thread), listed as Windows enumerates them with *Default*, *Communications*, *Muted* and the format; the default playback device is selected when the page opens. The selected device's panel (`AudioDeviceSettingsViewModel`, its template in `Views/AudioTemplates.xaml`, so KOS Equalizer shows the same panel) has *Make default* (console and multimedia roles) and *Default for communications*, the volume (written once the slider rests for 300 ms) and *Mute*, the format (the formats the device takes in exclusive mode at its channel count, one per bit depth and rate, applied with *Apply* through the Sound control panel's policy interface, with the mix format in 32-bit float), *Allow apps to take exclusive control* and *Give exclusive mode apps priority* (priority is stored only while exclusive mode is allowed) and *Turn audio enhancements off* (only on devices with effects; the others say they have none). Every control writes its own change, one at a time; the device is then read back and the toast says what it has: a warning when the read-back isn't what was asked, an error when the write failed or the device is gone, and the list is read again (another device may have lost the default). A note says that apps in exclusive mode, ASIO and kernel streaming bypass Windows' audio effects and equalizers. Writes were checked in code only, not on live devices.
- **Equalizer** (KOS Apps group) opens **KOS Equalizer**, an app of its own (`src/KosEqualizer`, `KosEqualizer.exe`, with its own icon, single-instance) like KOS Firewall: one page in the toolbox's `AppWindow`, always as administrator (`requireAdministrator`: the effect's registration, the endpoints' effect values and `%ProgramData%\TheKOS\Audio` are administrator-only). It's published to `equalizer\publish\win-x64` with `KosEqApo.dll` (`toolbox/apo`) beside the exe, outside the single file, and installed to `%ProgramFiles%\KOS\equalizer`; an elevated toolbox starts only the copy there owned by SYSTEM/Administrators, and KOS Engine's tray menu opens it too. The playback devices are on the left (as on the Audio page), plus any device KOS Equalizer is still on for that isn't connected (from the registration journal, matched by flow and GUID: it only offers *Turn off*, so its registration can go). A visit only reads: the profiles (`equalizer.json`), each device and KOS Equalizer's state on it (`EqRegistration.Status`). The selected device has, in cards: *KOS Equalizer on this device* (the state; *Turn on* / *Turn off*, which restart Windows Audio and run off the UI thread; the effect's own status line with its time; where Equalizer APO is on the device it says so before turning on, and once KOS Equalizer replaced it a warning toast and a lasting note say that turning off puts it back; *Changed since* and *Not available* show the reason; each click is reported from the state read back, a warning when turning off left values that were changed since as found). *Profiles* (the active one, or flat; *New*, *Duplicate*, *Rename*, *Delete*; the gamemode profile, or none, which KOS Engine plays while gamemode is on; names stay unique and the device's references follow a rename). The active and gamemode lists also offer a built-in *Footsteps (FPS)* preset (`EqPresets`): preamp -6 dB, low shelf 100 Hz -6 dB, peak 250 Hz -3 dB, peak 3 kHz +6 dB, peak 7 kHz +2.5 dB. No device uses it by default; picking it adds a copy to the device, edited from there. The master switch in the window's header is a bypass: off, every device KOS Equalizer is on for plays flat at once (a marker file, and the devices' settings files written flat, with no audio restart; the registration and the profiles stay), and on, each plays its profile again. *Play* and KOS Engine's gamemode switch keep it flat while it's off, and a warning toast names any device whose file doesn't read back as written. *Editor* for the active profile: parametric (up to 64 filters: on/off, type, frequency, gain, Q; numbers with a dot or a comma) or a 10, 15 or 31-band graphic equalizer (switching to graphic reads the curve at the sliders' frequencies; back to parametric keeps the bands), the preamp with *Suggested* (the preamp that keeps the curve at or below 0 dB), the response curve (`Equalizer.Curve`, 20 Hz–20 kHz on a log scale) and `EqSettingsFile.Problem` inline (invalid values or more than +24 dB: shown, not played). Edits apply live: 300 ms after the last one the config is saved and `EqConfig.Play` writes what the device plays now (nothing while KOS Equalizer is off for it; the gamemode profile during gamemode), off the UI thread, one write at a time, on a copy of the config; a config that couldn't be read is shown and never saved over. *Import and export*: Equalizer APO / AutoEQ text (`EqImport`) from a file (up to 1 MB) or pasted becomes a new active profile (a warning lists the lines left out); *Export…* writes the active profile as that text. Below them, the device's Windows audio settings: the Audio page's cards (`AudioDeviceSettingsViewModel`). Closing waits for pending edits and a turn on or off in progress. **Transparent taskbar (KOS Shell)** (Interface) is a switch the toolbox only writes (`HKCU\Software\TheKOS\Shell`, `TransparentTaskbar`); KOS Engine (`ShellHost`) does the work, for the Windows 10 and the Windows 11 taskbar. For every taskbar window it sets a transparent accent at each tick and again 250 ms and 1.5 s after a color, theme or display change or a new taskbar. Turning it off sends the taskbars a `WM_SETTINGCHANGE` for `ImmersiveColorSet`, which makes them redo their own look. The Windows 11 taskbar is XAML, which that accent doesn't reach: there the engine loads `KosShell.dll` (C++/WinRT, beside the engine) into Explorer through XAML diagnostics (`rundll32 KosShell.dll,Inject <pid>`, run with Explorer's token and only from a DLL owned by SYSTEM/Administrators). The DLL keeps `BackgroundFill` and `BackgroundStroke` under `Taskbar.TaskbarBackground` transparent, also when the taskbar sets its brush again, and puts the taskbar's own brushes back when the switch is turned off (events `Local\KosShell.<pid>.On` and `.Changed`). Crash guard: the Explorer the DLL goes into is journaled first, and if it ends within 30 s the DLL isn't loaded again until the switch is turned off and on (a balloon and the log say so). KOS Engine's status window has a *Transparent taskbar* line. Checked on the Windows 10 taskbar (transparent, Explorer's own reset undone, own look back when off, stays transparent with Start open and a maximized window) and, for the DLL's loading, tree callbacks, UI-thread switch and brush restore, with its probe build in the Start menu's XAML process. On the development PC's Windows 11 taskbar (2026-11-20): loaded within a second, the background transparent and its own look back twice through the switch, no Explorer crash; not yet on a stock Windows 11 install (VM checklist item 24).

**Dark Registry Editor**, **Dark management consoles**, **Dark classic Notepad** and **Dark Control Panel and Properties dialogs (KOS Shell)** (Interface) are switches the toolbox only writes (`HKCU\Software\TheKOS\Shell`, `DarkRegedit` / `DarkConsoles` / `DarkNotepad` / `DarkDialogs`).
- KOS Engine (`DarkApps`) watches top-level windows being shown, through an out-of-context window event hook that loads nothing anywhere, while one is on.
- The first window of `%windir%\regedit.exe`, `%windir%\System32\mmc.exe` or `%windir%\System32\notepad.exe` (full path) gets `KosShell.dll`, through a `WH_CALLWNDPROC` hook on that window's thread only, removed after one message.
- *Dialogs*: `%windir%\System32\rundll32.exe` only while it runs a Control Panel applet (`shell32.dll,Control_RunDLL` in its command line), `%windir%\System32\SystemProperties*.exe`, and `%windir%\explorer.exe` once it shows a dialog (`#32770`).
- In the app (`shell\KosDark.cpp`) the DLL checks its exe (and rundll32's command line) against the same list, then:
  - turns on the app's dark mode (uxtheme's app mode: dark popup and context menus) and dark title bars, except in File Explorer, which keeps its own;
  - darkens each window by class as it's created: tree and list views, headers, tabs, status bars, edits, combo boxes, buttons, rebars, the MDI client, dialogs (`WM_CTLCOLOR*`) and the menu bar. In File Explorer only dialogs and the windows inside them: its folder windows and the taskbar are left alone.
  - Confirmation boxes (task dialogs) keep their light body and buttons with a dark title bar: their text colors are fixed when the box is built, so a dark body made the text unreadable.
- No API is hooked and no other program gets the DLL: games never do.
- Turning a switch off applies the next time the app opens (File Explorer: its next restart); an open window stays dark until it's closed.
- Parts a console snap-in draws itself (Event Viewer's .NET panes) can stay light.

**Start menu** runs the KOS script with an argument (`1` = Windows, `2` = Open-Shell; with no argument the script still asks). The state is read from the system: the `StartMenuExperienceHost.exe` file in `SystemApps` (the script renames it to `.old`) and Open-Shell's *Start automatically for this user* option (`HKCU\Software\OpenShell\StartMenu\Settings\AutoStart`; absent = starts). Windows renames the `.old` back, waits for the file to appear (PowerRun returns before finishing) and only then turns off Open-Shell for this account: `AutoStart` = 0 and `StartMenu.exe -exit`, without uninstalling. Open-Shell deletes `AutoStart`, starts Open-Shell through Explorer (without the script's elevation), renames the Windows menu to `.old` and waits for the swap. Without Open-Shell installed, the card is unavailable. **Start menu search** is grayed out, with the reason, while Open-Shell starts with Windows or the Windows menu is turned off. **CTF Loader** follows ctfmon.vercel.app. *Suspended* writes `InputServiceEnabled` and `InputServiceEnabledForCCI` = 0 in `HKLM\Software\Microsoft\Input` (what KOS's RunOnce already does): `ctfmon.exe` stays in the process list, but idle. *Disabled* also changes the TextInputManagementService `ServiceDll` from `TabSvc.dll` to `MSCTF.DLL`, and the service fails to start. *Enabled* sets both values back to 1 and restores `TabSvc.dll`. Takes effect after a restart; apps keep typing through `MSCTF.DLL` in their own process.

Turning **Windows Firewall** off (it disables the mpssvc and BFE services) is refused while KOS Firewall is on: its filters live in the Base Filtering Engine. The check (`Tweak.Refuse`) runs in the toolbox before applying and again in the elevated process.

Re-enabling the firewall rules runs `netsh advfirewall reset` and deletes custom rules. The state compares the current rules with the Windows defaults (`SharedAccess\Defaults`): all present = enabled, none = disabled, some of them = partial. Rules that apps create after Advanced do not count.

**VBS** and **memory integrity** are separate. VBS: the `DeviceGuard` policy and `Control\DeviceGuard` values, System Guard, Credential Guard (`LsaCfgFlags` 2: enabled *without* the UEFI lock, so it can be turned off from Windows), `vsmlaunchtype` and, when enabling, `hypervisorlaunchtype` Auto; turning it off also clears `Mandatory` and the Credential Guard scenario. Memory integrity: the `HypervisorEnforcedCodeIntegrity` scenario (with `HVCIMATRequired`); it only runs with VBS on. Turning either off with Riot Vanguard or FACEIT installed (found by their services: `vgc`/`vgk`, `FACEIT`/`FACEITService`) adds what that anti-cheat can ask for to the warning toast (Vanguard: memory integrity, error VAN: RESTRICTION: 5; FACEIT: VBS and IOMMU on some accounts); it never blocks the change. LSA protection (`RunAsPPL`) stays its own setting, and kernel shadow stacks too. **Clear the VBS UEFI lock** (action in the same group): when VBS or Credential Guard was turned on *with* a UEFI lock, the setting is also kept in the firmware and Windows keeps VBS running after the registry turns it off. Only in that case (VBS running while nothing is configured to start it, read from `Win32_DeviceGuard`), it does Microsoft's documented steps: mounts the EFI partition, copies `SecConfig.efi`, creates the one-time boot entry with `DISABLE-LSA-ISO,DISABLE-VBS` and unmounts; at the next boot SecConfig asks for a key press and clears the lock. **Hyper-V** switches the whole stack through the script: the optional features (Hyper-V, Virtual Machine Platform, Windows Hypervisor Platform; read from what servicing recorded for each), the Hyper-V drivers and services (including `hvservice` and `HvHost`, which the KOS first boot disables), the `ROOT\VID` devices and, when enabling, the hypervisor at boot. Turning it off also disables the Hyper-V guest drivers. It replaces the "Prepare Hyper-V (part 1)" action. **PowerShell script execution policy** writes the machine value and the user one (which wins over it).

### Problems found in the original scripts

The toolbox reimplements these in C# with the correct values; the original scripts were not changed:

- `MS-Store Enable-Disable.cmd` and `Xbox Services Enable-Disable.cmd` write to `HKLM\SYSTEM\ControlSet\Services<name>` (a nonexistent path); the Xbox one also writes `XblAuthManage` instead of `XblAuthManager`.
- `MultiPlane Overlay.bat`: the enable option has a missing quote and fails.
- `IOPageLockLimit.bat`: the "according to RAM" option writes the total memory instead of the calculated value (option omitted).
- `set-int-steer-mode.bat`: the menu offers "[3] Default", but `choice -c 12` only accepts 1 and 2, and the third block tests `errorlevel 2` again, so the default is unreachable. Also, "Force" writes `InterruptSteeringFlags = 2`, which according to the script's own comment is the "disabled" bit (forcing would be 4).
- `MMCSS.bat` and `PowerThrottling.cmd` force a restart; the toolbox only marks "pending restart".

Fixed in the KOS scripts themselves (2026-11-08):

- `Printer Enable - Disable.cmd` turned on `Internet-Printing-Client`, `Printing-LPDPrintService` and `Printing-LPRPortMonitor`, features that don't exist on Windows 10/11 (the names are `Printing-Foundation-…`).
- `Nagle Algorithm.bat` listed the interfaces with `wmic`, which current Windows no longer has.
- `CFG Enable-Disable.cmd on` used `Set-ProcessMitigation -System -Remove -Disable CFG`, which fails with C000000D and changes nothing; it now clears the CFG bits of `MitigationOptions`.
- `Clipboard Enable-Disable.cmd` used `sc config cbdhsvc start=auto` (no space after `start=`, which sc refuses).
- `RunOnce.cmd` disabled the task `\Windows\UpdateOrchestrator\Start Oobe Expedite Work` without the `\Microsoft` prefix.
- `Safe FiveM-Minecraft Services.cmd` option 1 ("KOS default") turned DPS and DusmSvc on, while the KOS first boot turns them off.

## Known limitations

- **Interface little exercised:** only the Devices, Processes and Windows pages and search were opened on Windows (as administrator, 100% scale). Layout at high DPI, animations, keyboard navigation and the UAC flow still need to be seen.
- **Processors:** lists and masks cover only the first group (up to 64 logical processors), like `AssignmentSetOverride` and `Process.ProcessorAffinity`.
- **Tweaks without a KOS script:** the values are those found in Microsoft's documentation; the KOS scripts do not set them, so none has a KOS default.
- **No system operation has been tested on a real machine.** Test in the VM before using.
- **English names in the power editor:** they come from the fallback text stored in the Registry next to the MUI resource (`@...powrprof.dll,-NNN,Text`). This format has not been confirmed on a Windows in Portuguese; if missing, the setting appears with a technical label (GUID), without inventing names.
- **Scheduled tasks** are read through the Task Scheduler COM with dynamic calls; not verified on Windows. Tasks the user cannot read are counted and warned about (run as administrator to include them).
- **StartupApproved\Run32** for 32-bit HKLM entries follows what Task Manager uses; not confirmed in the VM. In HKCU, Windows does not separate 32 and 64 bit, so there is only one list.
- **BCD** can only be read as administrator. As a standard user, those cards show *Read error* and are blocked; use Settings › Restart as administrator.
- **VBS/HVCI** shows the configured state, not whether it is running right now.
- **Start menu on a standard account:** the script writes Open-Shell's *Start automatically for this user* option to the HKCU of whoever runs it elevated. On a standard account elevated with another administrator's password, it goes to that administrator's profile, and the toolbox reports that the switch was not confirmed (the Windows menu file was already swapped).
- **Several UAC prompts:** "Apply KOS defaults" as a standard user asks for UAC per tweak. As administrator, it asks for nothing.
- **Pinned hash:** only the script called is verified; files it calls are not.
- **Restoring custom values** only works on tweaks without a script and, if it involves system settings, with the toolbox as administrator.
- **Snapshot as a standard user:** if the Backups folder does not accept writing, the capture is done by the elevated process and, in that case, without a progress bar.
- **Peripherals:** every driver is tested with byte fixtures and a scripted transport. The Attack Shark R82HE (`3151:502D`, firmware 5.05, cable) on this PC: Identify 2844; polling 1000 → 8000 → 1000, brightness 0 → 50 % → 0, static red, breathing green, spectrum, static white and profile 1 → 2 → 1 written, read back and restored (the original per-key picture mode included), so it is a tested model; the switch columns backed up, 1.9 mm on every key written and read back, the backup written back and read back identical; rapid trigger on every key (0.1 mm steps) written, read back (each key's kind kept) and restored the same way; the key travel stream gave 7236 reports in 90 s for the keys pressed (0 → 3.65 mm at the bottom → 0 on release) and stopped cleanly; the keymap (four sub-layers and the Fn layer) read, the layout checked against it, a per-key actuation, the toggle mode, mod-tap, dynamic keystroke (the cell order checked by pressing: event A in bits 0..1, byte n for sub-layer n) and a remap (F12 → F13) on F12 written, read back and restored; snap tap on F11 + F12 written with single-slot partner writes, read back and restored identical to the backup (whole partner columns didn't read back); the macro write didn't store (so it isn't offered; all 50 slots read afterwards, the test steps in none); one per-key picture upload (a color per row, from the layout's slots) sent with no endpoint stall, every key's color confirmed by eye (the board can't read it back), then the lighting put back to picture mode at brightness 0 (the stored picture stays the test pattern: the earlier one couldn't be read to keep it). An Fn-layer entry (Fn+A → Left) written, read back and restored (the Fn layer identical afterwards). Not checked on hardware yet: whether the polling rate survives a replug. On hardware (this PC): the Viper Ultimate receiver (`1532:007B`, awake) read firmware, battery, live and stored DPI, stages, polling, sleep, low-battery threshold, brightness and effect; written and read back with the toolbox's driver: DPI (stored and live), brightness (stored and live), static color and spectrum. Polling, sleep and low-battery writes, the stage choice and the cable (`007A`) aren't checked on hardware, so `007A`/`007B` stay *Untested model*. The Mouse Dock (`007E`): firmware, serial, the ring's brightness and effect (led `0x05`; static color, live breathing, spectrum, each read back and restored); it reports no battery. The dock charge commands OpenRazer lists for the Viper (`03/10`, `03/01`) answer *unsupported* on this firmware, so the ring's battery colors come from KOS Governor, as Synapse does it. The governor's dock battery loop itself isn't checked on hardware yet. Not built yet: lift-off, Logitech 0x2202/0x8061, the ODM families' settings (battery only), GearHub, Wooting reads, VIA keymaps, Razer/Logitech/SteelSeries keyboards, the generic HID battery usage, XInput, the BlackShark V3 headsets (their handshake writes), HeadsetControl on the page. Vendor app process names (`RazerAppEngine`, `Razer Synapse 3`, `Razer Synapse Service`, `lghub`, `lghub_agent`) aren't checked on a real install.

## VM test checklist

1. Copy `publish\win-x64` to `C:\Program Files\KOS Toolbox` in the VM with KOS and open **without** administrator. Check Home (CPU/memory/GPU cards and details, post-install warnings, the log warning if any), Settings › About (KOS version and post-install) and whether the BCD cards show *Read error*.
2. Combos: check that no list shows a class name (open and closed), that the active plan appears as "Name — Active" and that lists with no match show the state in italics.
3. 150% and 200% scale, window at minimum size; navigation with Tab, arrows, Enter, Ctrl+F and F5. With Windows animations off, check that the transitions and smooth scrolling continue with *Enable animations* on; turn the option off and check that everything appears without transition.
4. Toggle a user tweak (Win+Shift+S, Alt+Tab) and a machine one (Notifications); cancel UAC once (nothing changes) and accept the second time. Use `⋯ › Restore previous state` and `⋯ › Details and source`.
5. Startup: Standard and Advanced; disable and re-enable a test Run entry, a Startup folder one and a test scheduled task; check in Task Manager. Open the Drivers filter (warning). Disable a test service and re-enable it (goes back to the saved type).
6. Power: select a plan that is not active, change an AC and a DC value, switch plans with pending changes (they are discarded, with a warning), apply and check with `powercfg /q`. Verify the English names. Make a copy of the plan, rename, export and import the .pow, delete the copy; on a test plan use *Custom value…*, *Remove value* and *Show in Windows power options* (check in Control Panel; the setting's `Attributes` value must change only in bit 1). Also confirm that deleting ACSettingIndex/DCSettingIndex with the Power service running takes effect immediately (`powercfg /q`) and turn on *Compare with other plans*.
7. Services: create `Custom.test` (with and without full export), compare, export CSV, change the type of a test service, restore only it and check the notification and the `PreRestore.*`.
8. Tools: check the list against the KOS tools folder, open an .exe and a shortcut, and a broken test shortcut.
9. Run as administrator and repeat 4–7. Restart the VM and check the *Restart required* badges.
10. Devices › Interrupts: on a test device, change the MSI mode and the priority, apply (UAC), restart, check in MSI Utility and use *Restore original*. Devices › Ghost devices: remove a disconnected USB device and reconnect it (Windows recreates it).
11. Processes: create a rule for `notepad.exe` (Below normal, processors `0-1`), *Start*, open Notepad and check in Task Manager; test *Stop* and *Start at sign-in* (after a new logon).
12. Storage: *Scan* C: and a folder; in Cleanup use *Analyze*, clean only "Your temporary files" and check the freed space; then a system category (UAC).
13. Apps: in Programs uninstall a test program and check that it disappears from the list. Install and uninstall an NSIS one (an Electron app) and an Inno Setup one, and check that the leftovers list appears. Delete the leftovers and check the `.reg` backup in `leftovers-removed`. Use *Force removal* on a test program. In Store apps (with Microsoft Store services enabled), remove a test app, check the leftovers and reinstall from the Store.
14. Network: change a test property (for example *Interrupt Moderation*), apply with restart, check in Device Manager and use *Restore original*.
15. Drivers: export a package to a folder and delete an old package that is not in use; check in `pnputil /enum-drivers`. In GPU › Driver: export the display driver first (Cleanup › Drivers), use *Remove display driver…* (the screen goes to the basic driver), restart and reinstall with *Install from folder…* pointing to the extracted (or exported) folder. On an NVIDIA PC: *Find drivers*, download one, leave only the required components, *Install* (clean), check the version on the card and that `C:\Program Files\NVIDIA Corporation` has no NVIDIA app; then *Clean and restart* with DDU, and once more with *Restart in Safe Mode and clean* (check that Windows comes back in normal mode and that `bcdedit` has no `safeboot`).
16. Display: add a safe timing (for example the native one at 60 Hz), save, restart the display driver, check in Settings › Display › Advanced display and use *Restore monitor EDID*.
17. BIOS (board with an AMI BIOS): copy SCEWIN to `tools\SCEWIN`, use *Read BIOS*, change a harmless setting (for example *Setup Prompt Timeout*) and apply. Check the backup in the *Backups* tab, restart and see the value in the BIOS setup. Then restore from the backup and check again.
18. Windows Update with Windows Update off (KOS default): *Search for updates*, install one small update (a Defender or .NET one), hide one and show it again; afterwards check that wuauserv, BITS and dosvc are Disabled and the two policies are back (`reg query HKLM\SOFTWARE\Policies\Microsoft\Windows\WindowsUpdate`). Setup › Microsoft Store: install a free app (Calculator, `9WZDNCRFHVN5`) with the Store toggle off, then with *App installs and licenses* off (refused with the reason). Setup › Updates: install an old Chocolatey package and an old GitHub program and check that both are listed and update.
19. Check the logs in Settings › Open logs folder and the permissions of the `Logs\Toolbox` folder (Users: Modify on it only).
20. Peripherals (on the PC with the devices, not the VM; as a standard user and as administrator): the list shows the Razer Viper Ultimate receiver (`1532:007B`) and the Razer Mouse Dock (`1532:007E`) and the `3151:502D` keyboard, with MI_00, MI_01 COL01–COL05 and MI_02 in its collections (plus any USB audio device with a consumer-control collection). *Copy device report* on each: paste it and check the seven collections are there and there is no `hid#` path or instance id. Unplug the receiver and plug it back with the page open: about 2.5 s later it leaves and comes back.

Peripherals hardware checklist (Viper Ultimate on its receiver, mouse awake: move it first): the row shows *Razer Viper Ultimate · Wireless receiver · 1532:007B* with the battery percent and *charging* exactly as Synapse shows them (close Synapse afterwards); Info shows the firmware. Log: which transaction id answered (`3F` or `FF`). Then, one at a time, change and change back, each confirmed by the toast and the value on the page: DPI (e.g. 800 → 1600 → 800), polling rate (1000 → 500 → 1000, measured in Latency › Mouse each time), sleep timer, low-battery threshold, brightness.
